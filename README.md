# КУРСОВАЯ РАБОТА

## Тема проекта

**Развёртывание и сопровождение веб-проекта с мониторингом, централизованным логированием и резервным копированием.**

## 1. Описание проекта

В рамках курсового проекта развёрнута инфраструктура веб-приложения на базе WordPress с балансировкой нагрузки между двумя серверами приложений.

Инфраструктура включает:

- Nginx — веб-сервер, обратный прокси и балансировщик нагрузки;
- два сервера WordPress;
- MariaDB — система управления базами данных с репликацией;
- Prometheus — сбор и хранение метрик;
- Grafana — визуализация метрик и мониторинг состояния инфраструктуры;
- Graylog — централизованный сбор и анализ системных журналов;
- отдельный сервер резервного копирования;
- маршрутизатор и межсетевой экран для разделения сетевых сегментов;
- Ansible — автоматизация развёртывания и настройки инфраструктуры.

Конфигурации и сценарии автоматизации хранятся в Git-репозитории на gitlab.com.

## 2. Архитектура инфраструктуры

Инфраструктура построена с разделением на три сетевых сегмента:

- WAN — внешняя и административная сеть;
- DMZ — демилитаризованная зона, в которой размещён фронтенд веб-приложения;
- INTERNAL — внутренняя сеть серверов приложений, баз данных и инфраструктурных сервисов.

Маршрутизацию между сегментами и фильтрацию транзитного трафика выполняет сервер `k-net`.

## 3. Веб-приложение

В качестве веб-приложения используется CMS WordPress.

Веб-инфраструктура построена по схеме с отдельным фронтендом и двумя серверами приложений.

### 3.1. Схема обработки запросов

1. Пользователь обращается к веб-сайту по HTTPS.
2. Запрос поступает на сервер `k-front`.
3. Nginx принимает запрос и распределяет нагрузку между двумя серверами WordPress.
4. Серверы `k-b1` и `k-b2` обрабатывают запросы пользователей.
5. Оба сервера приложений используют базу данных MariaDB.

Соединение между фронтендом и серверами приложений осуществляется по HTTP. Внешнее соединение между пользователем и фронтендом защищено HTTPS.

### 3.2. Адрес веб-приложения

`https://kurs.dmitlabs.com`

## 4. База данных и репликация

Для хранения данных WordPress используется MariaDB 10.11.14.

Развёрнуты два сервера баз данных:

| Сервер | Роль | IP-адрес |
|---|---|---|
| k-db1 | Primary | `192.168.7.21` |
| k-db2 | Replica | `192.168.7.22` |

Настроена репликация на основе GTID.

Основной сервер `k-db1` принимает изменения данных. Сервер `k-db2` получает изменения от основного сервера и поддерживает реплику базы данных.

Работоспособность репликации проверена.

## 5. Мониторинг инфраструктуры

Для мониторинга используется связка Prometheus, Node Exporter и Grafana.

### 5.1. Prometheus

Prometheus выполняет сбор и хранение метрик с серверов инфраструктуры.

Для получения системных метрик используется Node Exporter.

Настроено 9 целей мониторинга. Все цели находятся в состоянии `UP`.

### 5.2. Grafana

Grafana используется для визуализации метрик и контроля состояния серверов.

Настроен источник данных Prometheus и установлен дашборд Node Exporter Full.

### 5.3. Адреса интерфейсов мониторинга

| Сервис | Сервер | URL |
|---|---|---|
| Grafana | k-mon | `http://192.168.50.196:3000` |
| Prometheus | k-mon | `http://192.168.50.196:9090` |

## 6. Централизованное логирование

Для централизованного сбора и анализа системных журналов используется Graylog 7.2.2.

На сервере `k-log` развернуты следующие компоненты:

- Graylog;
- MongoDB 8.0;
- Graylog Data Node.

Настроен приём системных сообщений через Syslog UDP Input на порту `1514`.

Для передачи системных журналов с серверов используется rsyslog.

### Адрес веб-интерфейса Graylog

`http://192.168.50.197:9000`

## 7. Резервное копирование

Для хранения резервных копий используется отдельный сервер `k-backup`.

Настроено автоматическое резервное копирование базы данных MariaDB:

- выполнение ежедневно в 02:00;
- передача резервных копий на сервер `k-backup`;
- срок хранения резервных копий — 7 дней.

Проведена проверка восстановления базы данных из резервной копии.

## 8. Сетевая безопасность

Для маршрутизации и фильтрации трафика используется сервер `k-net` с межсетевым экраном UFW.

Основные принципы настройки:

- входящие подключения по умолчанию запрещены;
- исходящие подключения разрешены;
- транзитный трафик по умолчанию запрещён;
- разрешён HTTPS-трафик к фронтенду;
- разрешён HTTP-трафик от фронтенда к серверам WordPress;
- разрешены необходимые исходящие DNS, HTTP, HTTPS и NTP-соединения из внутренней сети;
- SSH-доступ к маршрутизатору разрешён для Ansible-контроллера и административных сетей;
- SSH-доступ Ansible-контроллера к фронтенду разрешён отдельным правилом.

Таким образом, серверы приложений и инфраструктурные сервисы размещены во внутреннем сетевом сегменте, а веб-фронтенд — в DMZ.

## 9. Автоматизация развёртывания

Для автоматизации настройки серверов используется Ansible.

Управление инфраструктурой выполняется с сервера `k-ans`.

Основная структура проекта:

```text
kursovaya/
├── inventory/
│   └── inventory.ini
│
├── playbooks/
│   └── *.yml
│
├── ansible.cfg
│
└── README.md
```

Назначение основных каталогов и файлов:

- `inventory/` — инвентарный файл с перечнем управляемых серверов;
- `playbooks/` — Ansible Playbook для установки, настройки и сопровождения компонентов инфраструктуры;
- `ansible.cfg` — конфигурация Ansible;
- `README.md` — описание проекта, архитектуры и порядка работы с инфраструктурой.

Настройка серверов и внесение изменений в конфигурацию выполняются с помощью Ansible Playbook.
